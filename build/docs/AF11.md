# AF11 — TRITIUM Android · «The first real release»

## Context

AF9b closed the last real code gap — a phone with no import path could not
receive another phone's history, which broke the maker's own stated
scenario, *"if I purchase a new phone in the future."* With that shipped,
the maker wrote a two-part roadmap for what comes after coding stops:
AF11 ships the first real, signed, installable release and proves it
against a genuinely large body of staged real-shaped data; AF12 (a
separate milestone, its own doc) audits the whole Android codebase and
fixes whatever it finds before the maker's own final decision — flipping
the release from **Pre-release** to **Release** — becomes the only thing
left to do by hand.

This is the milestone AF1.md originally reserved as AF10 (*"Signing,
GitHub Actions release workflow, README — the public release"*), renamed
and renumbered by the maker's own roadmap without moving what version it
lands on: `1.0`.

## §1 WHERE AF11 SITS

### 1.1 Signing, decided from the sibling Android port's own established convention

XTRITIUM §9.3 states the desktop's own rule plainly: no signing key is
ever stored on any server, and the signature is made on the maker's own
machine. The family's sibling Android port (`sudo-megas/SAAT`) already
has a real, working answer for exactly this problem on Android specifically
— `docs/ANDROID-RELEASING.md`, read in full — and AF1.md §2.2 already
pointed at it: `tritium.jks` was always meant to be made "the same way the
maker already made `saat.jks`." AF11 ports that convention rather than
inventing a new one:

| Decision | Answer | Source |
|---|---|---|
| Where the keystore lives | `~/.android/tritium-release.jks` — the real, active Android home for this checkout, mirroring SAAT's own `<project>/.android/<app>-release.jks` shape (SAAT's own copy lives in a project-local `.android/` instead only because the real `~/.android` was already TRITIUM's) | Confirmed directly with the maker |
| Keystore parameters | RSA 4096, PKCS12, 10950-day (30-year) validity, alias `tritium` — copied from SAAT's own documented `keytool` invocation | `SAAT/docs/ANDROID-RELEASING.md` |
| A new key, never a shared one | `tritium.jks`/`tritium-release.jks` is its own keystore, never a reuse of `saat.jks` — a compromise of one app's signing key must never reach the other's | AF1.md §2.2 |
| How a build reaches the key | Four Gradle properties (`TRITIUM_KEYSTORE_FILE`, `TRITIUM_KEYSTORE_PASSWORD`, `TRITIUM_KEY_ALIAS`, `TRITIUM_KEY_PASSWORD`), read from the environment or from `~/.gradle/gradle.properties` — both outside the repository. Absent, the release build type simply stays unsigned rather than failing configuration | `build.gradle.kts`'s `releaseKeystore(project)`, ported from SAAT's own function of the same shape, renamed |
| Where signing actually happens | **Never in CI.** `android-release.yml` builds and checks the tagged commit and produces an unsigned APK, exactly as `package.yml` already does for the desktop's own package (*"The package is NOT signed here... the signature is made on his machine"*). This is a deliberate divergence from SAAT's own CI-signs-via-GitHub-Secrets convention — closer to the desktop's own stated rule, and avoids a class of risk (a signing key value passing through a hosted CI runner at all) that SAAT accepts and TRITIUM does not need to | `package.yml`'s own header comment; XTRITIUM §9.3 |
| Verify before it's ever public | `apksigner verify --print-certs`, then a real `adb install` on the connected phone — both **before** the signed APK becomes a release asset, not after | Confirmed with the maker |

**Stated once, in the place a maker will actually read it before it
matters:** losing either `tritium-release.jks` or the two passwords in
`~/.gradle/gradle.properties` means no future Android update can ever be
installed over this release — every later build must be signed with this
exact key, forever. Back up the keystore file itself (not only the
passwords) to at least two offline places that do not fail together —
SAAT's own `docs/ANDROID-RELEASING.md` states this as the one truly
irreversible mistake in the whole process, and it is exactly as true here.

### 1.2 Versioning

`versionCode` held at `1` through every untagged milestone (AF1..AF9b),
matching SAAT's own `versionCode` holding at 1 through AM1..AM10 — this is
the first tagged release, so it moves to `2`. `versionName` moves from
`"0.9"` to `"1.0"`, landing on the exact version AF1.md's decision table
already reserved for "the public release" under its old name, AF10. Tag:
`android-v1.0` (AF1.md §1.1's `android-v*` prefix, disambiguating from the
desktop's own `v*` glob — confirmed neither `package.yml` nor any desktop
workflow triggers on it).

### 1.3 The release itself

`--prerelease`, titled "Android v1.0", with release notes written as an
ordinary release description — no pre-release-flavored hedging — so the
maker's only remaining action, per the roadmap's own words, is flipping
the toggle from Pre-release to Release. The unsigned CI artifact is never
attached to the public release page; only the verified, locally-signed,
`adb install`-tested APK ever becomes a public asset.

## §2 SCOPE IN

1. **`android/app/build.gradle.kts`** — `releaseKeystore(project)`,
   conditional `signingConfigs { release { ... } }`, `versionCode = 2`,
   `versionName = "1.0"`.
2. **`.github/workflows/android-release.yml`** — new. Triggers on
   `android-v*` tags and `workflow_dispatch` (a dry run that publishes
   nothing, matching SAAT's own reasoning: a tag is public and awkward to
   retract). Runs the full `check`, `assembleRelease` (unsigned, since CI
   never holds the keystore), a zero-permission sanity check on the actual
   built APK via `apkanalyzer` — one layer further out than
   `verifyReleaseManifestPolicy`'s own merged-manifest check — and uploads
   the unsigned APK as a workflow artifact only, never a release asset.
3. **Local, on the maker's machine** — `tritium-release.jks` generated;
   `~/.gradle/gradle.properties` holding the four `TRITIUM_*` properties;
   `android/app/build/outputs/apk/release/app-release.apk` built signed via
   `./gradlew assembleRelease` (the signing config makes this the same
   command that was already unsigned before AF11); `apksigner verify`;
   `adb install` on the connected phone; `gh release create --prerelease`.
4. **Phone reset** — every AF9b debugging/testing remnant removed, the app
   reinstalled strictly from the released asset, not a local build.
5. **The enrolled test** — one vehicle, same slug, built independently on
   both platforms: a desktop-native purchase history, then the phone as
   the ongoing device, synced across to the desktop over two real
   periodic cycles via the actual Export/Import buttons on both sides.

## §3 SCOPE OUT

- **No Play Store, no F-Droid, no IzzyOnDroid** — GitHub Releases only,
  AF1.md's own decision, unchanged.
- **No CI-side signing** — a deliberate divergence from SAAT's own
  convention, named in §1.1 rather than silently different.
- **No emulator-based release gate** — the same reasoning `android-ci.yml`
  already gives for skipping one; a real connected device is what this
  milestone actually verifies against.
- **No change to F16's bundle format** — AF11 ships and tests the format
  AF8/AF9b already agreed on; it does not widen it.

## §4 ACCEPTANCE CRITERIA

1. `tritium-release.jks` exists, opens with its recorded password, RSA
   4096, valid ~30 years. ✅ verified.
2. `./gradlew check assembleRelease` succeeds locally and the output APK
   verifies as signed (`apksigner verify --print-certs`, v2 scheme,
   4096-bit RSA, CN=TRITIUM). ✅ verified.
3. `android-release.yml` exists, path- and trigger-scoped correctly, never
   collides with `package.yml`/`android-ci.yml`.
4. A real `android-v1.0` tag push produces a green Actions run.
5. The signed APK installs on the connected device via `adb install` and
   launches.
6. A GitHub pre-release, "Android v1.0", exists with ordinary-sounding
   notes and the verified signed APK as its asset.
7. The phone carries no AF9b/AF11 debugging remnants and runs only the
   installed release build.
8. The desktop↔Android sync of one vehicle's history, built independently
   and non-overlapping on each side, then carried across by real periodic
   syncs, shows correct add/skip counts and an untouched `vehicle.toml`,
   confirmed both on disk and in the app's own rendering.
   ✅ verified — corrected from an earlier run of this criterion that
   tested two unrelated vehicles instead of one and was rejected outright
   by the maker (*"i mean what the fuck did you do right? the real
   ambition here is to collect immediate data of the same vehicle in the
   phone, then regularly (monthly etc.) to sync into the desktop"*); what
   follows replaces that run, not supplements it.

   One vehicle, slug `sportage`: the desktop given its own purchase-time
   history (2 fuel, 2 costs, 1 service, June 2024) through the real
   repository functions; the same vehicle built independently on the
   phone through the real Add-Vehicle and entry forms (named "Sportage",
   slugifying to the identical `sportage`), then carried across in two
   real periodic cycles:

   - **Cycle 1** — 3 fuel entries + 1 cost entry (July 2024) added on the
     phone through the real forms; real Export button tap → SAF save
     picker → `adb pull` → real desktop Settings → Import → "Choose a
     file…" → the GTK portal picker, opened by a real double-click.
     Result: *"Imported. 4 added, 0 already here."* `vehicle.toml`
     checksum-identical before and after; no `backups/` directory
     (nothing was overwritten, only added).
   - **Cycle 2** — one more fuel entry + one more cost entry (August
     2024), same real-form mechanism; the phone's full current state
     (all 4 fuel + both costs) exported again and re-imported the same
     way. Result: *"Imported. 2 added, 4 already here."* — skip-wins
     correctly recognised the 4 entries already carried over in cycle 1
     and added only the 2 genuinely new ones. `vehicle.toml` still
     checksum-identical; still no `backups/` directory.
   - **Checked in the app, not just on disk** — switched the desktop's
     own vehicle selector to the merged record. Fuel tab: all 6 entries
     in order, no duplicates, the row straddling the merge seam
     (02/07/2024, following the desktop's own 20/06/2024 row) computing
     6,540 l/100km — exactly what the 630 km / 41.200 L gap implies.
     Summary tab: Last Entries interleaves all 8 records (fuel, costs,
     and the desktop-only service entry) by date across both platforms;
     Lifetime reads 3.140 km / 244,100 l / 229.232,40 ₺, matching the
     merged record by hand.
   - **Mechanism, stated plainly** — every entry was created through the
     real on-device or on-desktop form, not a function call; both Export
     taps and both Import taps were real button presses (phone: `adb
     shell input tap` on coordinates read from `uiautomator dump`;
     desktop: `ydotool` mouse/keyboard input against the live,
     already-running Electron window, aimed by a `niri`-screenshot
     visual-servo loop, since this environment cannot launch a fresh
     Playwright/Electron instance against the maker's own display).
   - **Scope not covered** — both cycles moved fuel and cost entries
     only; no service entry crossed from phone to desktop, so that merge
     path shares the same code but wasn't independently exercised here.
   - One aside for the maker: the GTK save dialog silently inserts a
     literal space before the extension when a full filename is typed
     into it (`tritium-export-stage2. toml` landed on disk) — a
     DocumentsUI quirk, not TRITIUM's own behaviour.

   All synthetic data and test-only harness files from both the original
   and the corrected run (an androidTest probe, throwaway vitest scripts,
   the desktop's own `sportage` test vehicle) were removed or set aside
   afterward — none were committed.

## §5 EXIT

Tagged `android-v1.0`, versionCode 2. The pre-release stands until AF12's
codebase audit resolves — untouched if nothing needed fixing, superseded
by a fresh `android-v1.1` pre-release if it did. The maker's own two
reserved actions — README badges, and the final Pre-release → Release
flip — happen only after AF12 closes.
