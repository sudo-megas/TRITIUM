# TRITIUM — F2 · v0.1.1 · «Storage Layer»

Repo path of this file: `~/REPO/build/docs/F2.md`
Governing document: `~/REPO/XTRITIUM.md` — where this file and XTRITIUM disagree, XTRITIUM wins.

F2 turns the single-file settings store F1 built into the whole data layer of
XTRITIUM §4 — every record shape, on disk, exactly as §4.4 draws it. No screen
displays any of it yet. The point is that when F3 opens the vehicles pane, the
storage beneath it is already written, already tested, and already the only way
bytes reach the disk.

## 1. WHERE F2 SITS

The F-map in `F1.md` §1 is confirmed for this milestone: **F2 · v0.1.1 · storage

F1 already delivered the foundations F2 generalises:

| Already built (F1) | What F2 does with it |
|---|---|
| `writeFileAtomicSync` — temp + fsync + rename | stays **the only write path**; every record file goes through it |
| `dataDir()` · `settingsPath()` · `vehiclesDir()` | joined by per-vehicle directory resolution |

F2 writes no new write path, no new path resolver, and no new file convention.
It applies the existing ones to the rest of the model.

## 2. SCOPE — IN

### 2.1 The record shapes

All four of XTRITIUM §4.4, typed and guarded in `src/shared/records.ts`:

- **`vehicle.toml`** — a flat table. `name`, `make`, `model`, `year`, `engine`,
  `fuel_spec`, `plate`, `vin`, `tank_capacity_l`, `purchase_date`,
  `purchase_price`, `registration_date`, `inspection_due`.
  **No photo field. Vehicles have no photos anywhere in TRITIUM.**
  `inspection_due` is passive reference only — nothing watches it, nothing notifies.
- **`fuel.toml`** — `[[entry]]` per fill-up: `id`, `date`, `odometer_km`,
  `litres`, `price_per_litre`, `full_tank`, `fuel_type`.
- **`costs.toml`** — `[[entry]]`: `id`, `date`, `group`, `category`, `title`,
  `amount`, `income`, `payment_method`, `bank`, `instalment`, `note`.
- **`service.toml`** — `[[entry]]`: `id`, `date`, `part`, `odometer_km`,
  `amount`, `vendor`. `vendor` holds a pasted address and is **selectable text
  only, never a link** (XTRITIUM §3.5).

The fixed vocabularies ride here as data, not as strings scattered through the
code: `group` = `ilk-alis` | `tekrar-eden` | `manual`, the §6.1 category tree,
and the fuel-type pick-list.

### 2.2 Scaled integers — `src/shared/scaled.ts`

XTRITIUM §4.3. Files carry the human figures as entered; **all arithmetic runs
on scaled integers — money ×100, litres and price ×1000** — converted once at
load. Sums are exact; no float drift reaches a total.

The conversion is symmetric: a value read as `73.38` becomes `7338`, and is
written back as `73.38`. **Decimals are a property of the field, not of the
file** — money at 2 (`purchase_price`, `amount`), pump figures at 3 (`litres`,
`price_per_litre`), and `tank_capacity_l` at 1, exactly as §4.4 samples it as
`54.0`. Each renders straight from its integer, so `amount = 11746.00` stays
`11746.00` and does not degrade to `11746`. This is the piece F4's consumption engine and F5's cost
model both stand on, so it is tested to the cent and the millilitre here.

### 2.3 Schema versioning

XTRITIUM §4.2. Every file carries `schema_version = <int>` first. On read, an
older version is upgraded **in memory** and written back on the next save.
**No migration framework** — a version switch in the parser, nothing more.
All four files start at `schema_version = 1`.

### 2.4 The record files — `src/main/storage/{vehicle,fuel,cost,service}-file.ts`

One module per file, each a sibling of `settings-file.ts` in shape:
`parseX` / `serialiseX` / `readX` / `writeX`, schema stamped first, and
**unknown keys preserved untouched** — plaintext the maker can repair in Neovim
must never lose a line because the milestone that wrote it did not recognise a key.

**One deliberate departure from `settings-file.ts`.** A corrupt `settings.toml`
falls back to defaults, because losing a palette choice costs nothing. A corrupt
**data** file must never do that: falling back to "no entries" and then saving
would erase the maker's records. A data file that will not parse is **reported
and left exactly as it is** — never overwritten, never silently emptied.

Two details that will bite if left implicit:

- **Dates** are TOML local dates (`2026-08-16`), not strings. They must survive
  the round trip unquoted.
- **`total` is derived and never stored** (§4.4). If a `total` key is found in a
  file, it is dropped on read and never written back.

### 2.5 Vehicle directories & the repository — `src/main/storage/repository.ts`

- `vehicles/<vehicle-slug>/` resolution, the directory created through the same
  atomic helper.
- **Slug derivation is explicitly transliterated** — `ı ğ ş ö ç ü İ` mapped by
  an explicit table, never `toLowerCase()` on a Turkish `I` and never a
  locale-aware call (XTRITIUM §3.6, and `audit-locale` forbids it outright).
  Collisions get a numeric suffix.
- Whole files in at launch, whole files out on change (§4.1).
- **Id allocation** — `f-0001`, `c-0001`, `s-0001` — computed from the highest
  id already in the file, so a hand-edited file cannot produce a duplicate.

### 2.6 Settings completed to §4.4

F1 owned `language` and `palette` and deliberately carried `currency`,
`[units]` and `[format]` through as opaque blobs. F2 gives them real types,
real defaults and real guards: `currency`, `distance`, `volume`, `consumption`,
`decimals_consumption`, `decimals_cost_per_km`.

**`currency` carries no default.** §4.4 shows `currency = "TRY"` because it
samples a file that has already been through first launch. The key is **absent
until F3 asks the question once**, and its type is optional — if F2 stamped a
default, F3's ask-once would be dead on arrival against a file that already
answered it. Every other key defaults. The unknown-key mechanism stays
for keys later milestones add. **The settings UI is F11**; only the schema lands here.

### 2.7 The IPC surface

`src/preload/index.ts` grows in the F1 style — small, explicit, enumerated; no
generic "invoke anything" bridge. Six channels: `vehicles:list`, `vehicle:load`,
`vehicle:save`, `fuel:save`, `costs:save`, `service:save`.

**One load, four saves** — not a read and a write per file. §4.1 reads whole
files at launch, so a vehicle arrives as one bundle (its record and all three
entry files together); writes stay per file so that saving a fill-up cannot
rewrite the costs. A channel that meets an unparseable file **rejects**, so §2.4
holds across the bridge too: the renderer is told, and the file is left alone.

No renderer code consumes any of this yet; F3 is its first customer.

### 2.8 Tests that must exist

- **vitest:** round-trip per record type against the literal §4.4 samples ·
  scaled-integer exactness on a sum that would drift in floating point ·
  `schema_version` stamped, and an older version upgraded on read and written
  back on save · a corrupt data file is reported and **left untouched** ·
  unknown keys survive a write · id allocation continues from the highest
  existing id · `total` is never written · slug transliteration of a Turkish
  vehicle name.
- **Playwright:** the shell still launches and settings still persist — there
  is no new UI to drive, and that is the point. One spec does cross the bridge:
  the six channels are called from the renderer against a vehicle on disk, so a
  name that does not match between preload and main fails here rather than in F3.

## 4. ACCEPTANCE CRITERIA

F2 is done when every line below is true:

1. `npm test` is green: the four audits, `tsc --noEmit` silent under `strict`,
   all §2.8 units, the build, and the e2e suite.
2. Writing each of the four record types produces a file that matches its
   XTRITIUM §4.4 sample exactly — same keys, same order, same decimals — **plus
   the `schema_version` header**, which §4.4 elides in its entry samples and
   §4.2 requires. Where the two read differently, §4.2 wins.
3. `schema_version = 1` is the first line of every file written.
4. A file carrying an older `schema_version` is upgraded in memory on read and
   written back on the next save, without a migration framework.
5. Unknown keys in any record file survive a read-modify-write untouched.
6. A corrupt data file is reported and left byte-for-byte unchanged on disk —
   the app never overwrites what it could not parse.
7. Money and volume arithmetic is exact: a sum of a hundred entries matches the
   scaled-integer total to the cent, with no floating-point drift.
8. `total` never appears in a written `fuel.toml`, and is discarded if present.
9. A kill-mid-write against `fuel.toml` leaves the previous version intact —
   the F1 torn-write harness, pointed at a record file.
10. `writeFileSync` appears nowhere in `src/` outside `atomic.ts`: one write path, still.
11. A vehicle named in Turkish produces a correct slug with no locale-aware call.
12. Zero network; the audits still prove it statically and the offline e2e run
    still behaves identically.
13. No AI attribution exists anywhere in the tree or the git history.
