# TRITIUM — F16 · v0.2.6 · «Import»

Repo path of this file: `~/REPO/build/docs/F16.md`
Governing document: `~/REPO/XTRITIUM.md` — where this file and XTRITIUM disagree, XTRITIUM wins.

The maker buys fuel away from his desk. The laptop is not at the pump, so the
entry is made on a phone, and the Android app is where the data will actually
live day to day. **Once a month he brings that month across to the Arch desktop**,
which is where the charts, the statistics and the dense tables are.

The direction is settled and it is one way: **the phone exports, the desktop
imports.** F16 gives TRITIUM an import and no export.

Two things make this bigger than a button.

**The Android app does not exist yet.** So this document is not only a milestone
record, it is a **specification the unwritten app must satisfy** — §2.2 is the
format, and it is the Android phase's build order. Getting it wrong hands AF1 a
format it cannot produce.

**The constitution currently forbids the feature.** That is §1.1, and it is the
part of this milestone worth reading twice.

## 1. WHERE F16 SITS

**F16 is v0.2.6.** The desktop phase was declared finished at F14 and then twice
wasn't: F15 fixed what running the application revealed, and F16 adds the one
capability the Android phase cannot begin without.

### 1.1 A clause that was recorded as a decision and was not one

`XTRITIUM.md` §4.1 says, today:

> Backups are the user's business: copy the directory, or point RESONANCE at it.
> **The app ships no backup feature, no export feature, no import feature, no MIME
> type.**

That is not a small sentence. It is quoted as binding scope by **five** milestone
documents — F2, F3, F7, F8 and F11 all cite §4.1 by number when they rule export
or import out — and `README.md` tells the public "There is no export feature
because none is needed."

Asked about it, the maker's answer was that **he never wrote it.** It was
improvised into the constitution when the document was drafted.

This matters more than a scope change, because XTRITIUM opens by claiming:

> Every decision below was made deliberately, one at a time, before a line of code
> was written.

For §4.1's ban that claim is **false**. So F16 is not overriding a ruling. It is
correcting a clause that was *recorded as* a ruling, on the word of the only
person who could have made it — and correcting it in the open, with a dated note,
because that is what §0 requires and what `issues.md` I-10 cost this project ten
milestones to learn.

The amendment is deliberately **narrow**. Import is permitted, and the backups an
import needs. Export stays banned, because the phone exports and the desktop has
no reason to. The MIME type stays banned, because nothing has asked for one and
`packaging/README.md` says there is no custom file format to claim. Those two
survive not on the clause's authority — it has none — but because they are still
true.

**The five F-documents that quote the ban are left exactly as they are.** They
recorded what was true for their own scope. Editing them to agree with today is
the silent drift §0 forbids.

### 1.2 A gap in §9.1, and it is mine

## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

**1 — One TOML file, not an archive.**

The family precedent is SAAT, whose README describes a **ZIP bridge**: *"Settings
→ Export writes a ZIP holding exactly the `watches/` folder in the layout the
desktop app uses — so unzipping it into your desktop collection is the import on
that side."*

F16 does not copy that, and the reason is the difference between the two apps.
**A watch carries an `images/` folder; a TRITIUM record is text and nothing else**
(§7 — vehicles have no photos anywhere). SAAT needs a container because it has
binary payload. TRITIUM has none, so a container would buy nothing and cost a new
runtime dependency: Node ships no ZIP writer, and this project's eight runtime
dependencies are all UI or data.

One TOML file needs **no new dependency** — `smol-toml` is already here — and
stays greppable, diffable and repairable in Neovim, which is the argument §3 makes
for plaintext in the first place.

**2 — Ids do not cross the boundary, and this is not a preference.**

An id like `f-0001` is a **file-local, non-monotonic label**. `nextId` recomputes
it from the highest id present, every time; there is no stored counter; deleting
the highest entry *frees its number for the next one*. The storage layer says so
itself: *"nothing outside the file ever refers to an id."*

Two consequences, and the second is worse than the first:

- Two devices numbering independently will both mint `f-0005` for their fifth
  fill-up. There is no coordination and cannot be.
- **Duplicate ids inside one file corrupt it silently.** `entryRest` is keyed by
  id, so the second entry's unknown keys overwrite the first's on the next save;
  and `updateFuelEntry`/`removeFuelEntry` find by `findIndex`, so the second entry
  becomes **unreachable from the interface and impossible to delete**.

So **the bundle carries no ids at all**, and every incoming entry is renumbered on
arrival from the receiving file. Identity across the boundary is carried by facts
about the world — a date, an odometer reading — never by a bookkeeping label.

**3 — "Skip what you already have", with a key per kind.**

SAAT's rule, and it transfers: *"watches you already have are skipped rather than
overwritten, so re-importing is never destructive."* What does not transfer is how
you tell. A watch is a folder; a TRITIUM record is one `[[entry]]` among many in a
shared file, so the check is per entry:

| Kind | Two entries are the same record when they share |
|---|---|
| fuel | `date` + `odometer_km` |
| service | `date` + `odometer_km` + `part` |
| costs | `date` + `category` + `amount` |

Fuel needs no more: you cannot fill up twice at one reading on one day. Service
needs `part` as well, because tyres and an oil change on the same day at the same
reading is perfectly ordinary. Costs carry **no odometer at all**, so they are
identified by what a bill actually is — a sum, in a category, on a day.

**The consequence, stated plainly because it is the one thing this design loses:**
an entry edited on the phone *after* a previous import is **skipped, not
updated**. The desktop keeps its copy. Skip-wins never destroys a record, and it
does not carry a correction either.

**4 — Nothing is destroyed quietly.**

SAAT again, verbatim: *"Before any destructive change the previous version is
copied into `backups/` (newest 20 kept)."* F16 adopts it. Before an import writes
anything, every file it is about to touch is copied into
`~/.local/share/tritium/backups/<timestamp>/`, and the twenty newest are kept.

`backups/` sits beside `vehicles/` at the data root, which is safe by
construction: `listVehicleSlugs` walks only `vehiclesDir()` and further requires a
`vehicle.toml`, so nothing in the application can mistake a backup for a vehicle.

**5 — A bundle this build does not understand is refused, not rewritten.**

The storage layer reads `schema_version` and then **always writes back the current
constant**. A file stamped `2` that this app touches comes back stamped `1`, with
no warning — its own unit test asserts that as intended behaviour for *upgrades*,
but nothing stops it happening to a file from the *future*.

That is survivable inside one app. Between two apps it is a data-loss engine: the
phone ships a newer format, the desktop silently downgrades the stamp, and the
next reader believes a lie about what it is holding. **The importer therefore
refuses a `format_version` it does not know**, and says so.

**6 — The file is chosen through a native dialog, and that is allowed.**

`audit-overlap` bans the HTML `<dialog>` element, `showModal()` and
`role="dialog"`. It does not ban Electron's `dialog` module, and the distinction
is the one the audit's own text draws: *"a dialog element covers content; forms
open as real windows."* The banned thing is a surface Chromium paints **inside**
the application's window. An OS file picker is drawn outside the DOM entirely, and
F4b's D1 table already answers "modal confirmation" with "a real second window".

There is **no precedent for a native dialog in this application** — this is new
ground the rules do not forbid rather than a path already walked, and it is
recorded that way.

Two consequences follow, and both are handled rather than discovered:

- `audit-strings` scans **only `.tsx`**. A dialog title written in main-process
  TypeScript would escape the gate that keeps every visible string in the
  catalogues. So the renderer resolves the string with `t()` and passes it across
  the bridge; main invents no user-visible text.
- Playwright cannot see a native dialog. So `data:import` **takes a path**, and
  the picker is the renderer's job — the channel is testable without stubbing an
  OS surface.

### 2.2 THE FORMAT — the Android app's build order

Every key is the key the record files already use. That is not tidiness: it is
what lets the desktop parse a bundle with `FUEL_SPEC`/`COST_SPEC`/`SERVICE_SPEC`,
the **same readers** it uses for its own files, so the two can never drift.

```toml
format = "tritium-export"
format_version = 1
exported = 2026-08-19          # local calendar date on the device that wrote it
source = "android"             # free text; "who made this file"

[[vehicle]]
slug = "sportage"              # how the desktop finds the vehicle this belongs to
name = "SPORTAGE 1.6 T-GDI"
make = "Kia"
model = "Sportage"
year = 2025
engine = "1.6 T-GDI"
fuel_spec = "Kurşunsuz 95"
plate = ""
vin = ""
tank_capacity_l = 54.0
purchase_date = 2025-04-25
purchase_price = 2160000.00
registration_date = 2025-04-26
inspection_due = 2027-04-01

[[vehicle.fuel]]
date = 2026-08-16
odometer_km = 19764
litres = 29.990
price_per_litre = 73.380
full_tank = true
fuel_type = "Kurşunsuz 95"

[[vehicle.costs]]
date = 2026-04-11
group = "tekrar-eden"          # "ilk-alis" | "tekrar-eden" | "manual"
category = "trafik-sigortasi"
title = "Trafik Sigortası 26/27"
amount = 11746.00
income = false
payment_method = "kredi-karti"
bank = "Enpara"
instalment = "Taksit 6"
note = ""

[[vehicle.service]]
date = 2025-05-14
part = "Michelin Primacy 4 S1 235/50R19 103V XL"
odometer_km = 370
amount = 8664.00
vendor = "https://www.lastikcim.com.tr/…"
```

Binding rules for whoever writes this file:

- **No `id` key on any entry.** Decision 2. An id present is ignored.
- **No `total` key.** Derived values are never stored (§3.7) and it is stripped on
  read anyway.
- **Dates are bare TOML local dates** — `2026-08-16`, unquoted. Not a quoted
  string, not an RFC3339 datetime. TOML local dates carry no zone, which is the
  whole reason a fill-up cannot shift a day crossing between devices.
- **Figures are written as entered**, human-readable — `29.990`, `11746.00` —
  exactly as §4.3 requires of the record files. The reader scales them.
- **A vehicle is matched by `slug`.** Absent on the desktop → it is created from
  this table. Present → **the existing `vehicle.toml` is left alone**; a bundle
  adds entries to a vehicle, it does not rewrite the vehicle.
- Multiple `[[vehicle]]` blocks are allowed; each carries its own record arrays.
- A vehicle with no records at all is legal, and imports as a vehicle.

## 3. SCOPE — OUT

**No export.** The phone exports; the desktop has no reason to, and §4.1's ban on
it stands. No MIME type, no file association, no `%f` in the desktop entry — a
bundle is opened through the app, not by double-clicking it. No network of any
kind: a file moves on a cable, and §3's "Zero network. Ever." is untouched by this
milestone. No merge that overwrites — skip-wins, decision 3. No automatic import,
no watched folder, no import on launch: it happens when the maker asks and never
otherwise (§3.3 — only realised data, and nothing the maker did not do). No
conflict-resolution interface: there is one rule and it is written down.

## 4. ACCEPTANCE CRITERIA

F16 is done when every line below is true:

1. `npm test` green: seven audits, both tsconfigs under `strict`, units, build,
   e2e.
2. A **hand-written** bundle — typed in an editor, never produced by this app —
   imports, and its entries appear in the interface without a restart.
3. Importing the same bundle twice adds nothing the second time, and the record
   files are byte-identical across the second import.
4. No entry in any record file carries an id from a bundle; ids are the receiving
   file's own, allocated from its highest.
5. A bundle with a higher `format_version` is **refused**, nothing is written, and
   the maker is told why.
6. A malformed bundle leaves every file on disk byte-for-byte as it was.
7. `backups/` holds the previous copy of every file an import touched, and never
   more than twenty.
8. Every user-visible string, **including the file dialog's title**, resolves from
   the catalogues.
9. The three new gates are proved to bite — the defect reintroduced and the test
   watched to fail — for id carry-through, the version guard, and the broadcast.
10. `XTRITIUM.md` §4.1 carries a dated amendment saying what was corrected and
    why, and §9.1 prints F15 and F16.
11. No AI attribution anywhere in the tree or the history.
