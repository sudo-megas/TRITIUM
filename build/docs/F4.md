# TRITIUM — F4 · v0.1.3 · «Fuel»

Repo path of this file: `~/REPO/build/docs/F4.md`
Governing document: `~/REPO/XTRITIUM.md` — where this file and XTRITIUM disagree, XTRITIUM wins.

F4 is the first milestone that **computes**. F2 stored figures and F3 displayed them;
F4 derives one that exists in no file — litres per hundred kilometres, between
consecutive full tanks — and puts the two entry paths §5.1 asks for in front of it.

A stored figure that is wrong is visible: it is on the screen and in the file, and the
maker can see it. A derived figure that is wrong is invisible until it has been wrong
for a year. So the algorithm, not the forms, is what this milestone is really about.

## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

1. **Quick-add asks exactly three fields.** §5.1 is literal — "odometer, litres,
   price/litre — done." Everything unasked takes a default: `date` = today,
   `fuel_type` = the vehicle's own `fuel_spec`, `id` allocated in the main process, and
   `full_tank = true`. That last is not filler: a `false` default would mean the path
   built for the common case never produces a consumption point at all. A mis-flag is
   fixable in the full form; a silent stream of partials is a dead engine.
2. **The full form is also the edit path.** §3.8 — all entries are editable at any time —
   and quick-add's own promise that everything else is "editable later". `FormRequest`
   grows `entry?: string` beside the `slug` it already carries.
3. **A fill-up is added by the main process.** `fuel:add(slug, entry)` reads `fuel.toml`,
   allocates the id, appends and writes, exactly as `vehicle:create` allocates the slug
   *there* and nowhere else. A form window that has been open for an hour cannot hand
   back a whole stale document and lose what was written meanwhile. Editing an existing
   entry keeps the whole-document `fuel:save`, as the vehicle form does.
4. **The fuel write broadcasts.** `vehicle:save` and `vehicle:create` already tell every
   window; the three entry saves did not. Without it a fill-up saved in a form window
   would never reach the shell, which would go on showing the file as it was when it
   last rendered.
5. **Consumption is computed only between consecutive full tanks** (§5.2), on scaled
   integers, in one pure module, and is **never stored** (§4.4).
6. **l/100km only.** §5.2's formula is literally l/100km. F11 owns units *whole* — entry
   as well as display, km/mi and l/gal along with km/l and mpg — and half a unit system
   is worse than a deferred one. `decimals_consumption` (default 2) is honoured, because
   precision is display-only and already in the file.
7. **The fuel pane is provisional.** Two buttons and a plain list, so the engine has an
   output that can be looked at. F7 replaces it.
8. **F4 deletes nothing.** A mis-entered fill-up is edited. Removing one belongs with
   F7, where the list lives; the plaintext promise means a text editor can do it today.
9. **Today's date is built from the local calendar** — `getFullYear`/`getMonth`/
   `getDate`, never `toISOString().slice(0, 10)`. This machine is UTC+3: a fill-up
   entered at 01:00 would otherwise be filed on yesterday. `audit-locale` cannot catch
   this, because it is not a locale call.

### 2.2 The consumption engine — `src/shared/consumption.ts`

XTRITIUM §5.2, transcribed and not improved upon:

- sort a vehicle's entries by odometer;
- a data point exists **only** at a full-tank entry that has an earlier full-tank entry
  before it;
- `litres` = this entry's litres **plus every partial fill's litres in between**;
- `distance` = this odometer − the previous full entry's odometer;
- `l/100km = litres ÷ distance × 100`;
- partial entries and the first-ever entry produce **no** point.

The arithmetic runs on §4.3's scaled integers and rounds once, at the end:
`l100 ×1000 = round(litres ×1000 × 100 ÷ distance)`. A `distance` of zero or less
produces **no** point. Sorted by odometer, the only way a distance is not positive is two
entries at the same reading, which measures nothing and so says nothing; a backwards
odometer — which §5.1 accepts — sorts by the number it carries and closes its intervals
like any other.

There is no tank-level estimation anywhere, and there is none here: an app that targets
precision does not guess (§5.2).

### 2.3 Quick-add — `src/renderer/forms/FuelQuickAdd.tsx`

Three inputs and a Save, in a window of its own (§5.1 — movable, non-anchored). The
previous odometer is shown as a hint beside the field. A **backwards odometer warns and
is then accepted** (§5.1, §3.8): typos in old entries must be fixable, and the maker's
word is final.

The **total is derived and shown live** — `29,990 l × 73,380 → 2.200,67 ₺` — and never
written (§5.1, §4.4).

### 2.4 The full form — `src/renderer/forms/FuelForm.tsx`

Every field of §4.4's `fuel.toml`: date, odometer, litres, price per litre, the full-tank
flag as a real checkbox, and `fuel_type` from the fixed pick-list. Opened empty for a new
fill-up or on an existing `entry` id to edit one. Same live total, same odometer hint,
same warn-then-accept.

### 2.5 The fuel pane — `src/renderer/panes/FuelPane.tsx`

Provisional. The two buttons, disabled with no vehicle selected the way `vehicle-edit`
already is, and a list of the vehicle's fill-ups: date, odometer, litres, price, the
derived total, whether the tank was filled, and the l/100km at each entry that has one.
It reads `bundle.fuel.entries` from the store that already holds the whole vehicle —
no second read of the file, no second store.

### 2.6 Tests that must exist

- **vitest:** the §5.2 algorithm against its own wording — a partial between two fulls
  summed into the later one · the first-ever entry yielding nothing · a trailing partial
  yielding nothing · entries handed over out of order sorted by odometer, so one typed
  with a lower reading lands where its number says · two entries at the same reading
  yielding no point · a mis-flagged entry shifting the figures on both sides of it · the
  derived total matching §5.1's own example to the kuruş.
- **Playwright:** quick-add opens a **second window** · three figures land as one
  `[[entry]]` with `id = "f-0001"` and **no `total` key** · a `total` written into the
  file by hand is dropped on the next save · the shell shows the new fill-up **without a
  restart** · a second full tank makes the consumption figure appear and the first does
  not · the full form reopens an entry with every figure identical · all of it with the
  network severed.

## 4. ACCEPTANCE CRITERIA

F4 is done when every line below is true:

1. `npm test` is green: the four audits, both tsconfigs silent under `strict`, the units,
   the build, and the e2e suite.
2. A fill-up entered through quick-add lands in `vehicles/<slug>/fuel.toml` as one
   `[[entry]]` in the §4.4 shape, with an allocated `id`.
3. **No `total` key is ever written**, and one present in a hand-edited file is dropped
   on the next save.
4. Consumption appears only at a full-tank entry that has an earlier full-tank entry
   before it, and equals litres ÷ distance × 100 with every partial in between included.
5. The first entry, a trailing partial, and an interval of zero or negative distance
   produce no consumption figure.
6. A backwards odometer warns and is then accepted.
7. The shell shows a fill-up saved in a form window without being restarted.
8. Both entry paths are genuine second windows, movable outside the main one, and
   `window.open` is still refused.
9. Every figure renders in the family convention — `1.234,56 ₺`, `GG/AA/YYYY` — in both
   languages, with no `Intl` call and no locale read.
10. A figure typed into either form, saved, and reopened is the same figure.
11. `writeFileSync` appears nowhere in `src/` outside `atomic.ts`.
12. Zero network: the audits still prove it statically and the offline e2e run still
    behaves identically.
13. No AI attribution exists anywhere in the tree or the git history.
