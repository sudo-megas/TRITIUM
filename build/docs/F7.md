## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

1. **One table, three uses.** A single `EntryTable` driven by TanStack column
   definitions; each pane supplies its columns and its detail rendering and
   nothing else. Three hand-written `<table>` elements drifted apart in three
   milestones, which is precisely how the fuel pane ended up with a comment
   about column widths that the cost pane had to repeat.

2. **The chips filter by date, and by nothing else.** §7 is blunt: "Search —
   None. Filtering is the range chips." The five of §7.2 — **All time · YTD ·
   Previous year · This month · Previous month** — plus the custom range §7.2
   also asks for. No text filter, no category filter, no faceting. A list of six
   hundred records over a decade does not need one, and adding it would be
   inventing a requirement the constitution declined.

3. **The range decides what is SHOWN, never what is COMPUTED.** This is the
   decision the milestone turns on.

   §5.2's consumption figure exists only between consecutive full tanks, and it
   sums every partial fill in between. Hand the engine a filtered list and every
   one of those statements becomes a lie: the first full tank inside the window
   loses the earlier one it measures against, a partial fill just outside the
   boundary stops being counted into the tank that consumed it, and the figure
   that comes out is not "consumption for this period" — it is **a wrong number
   that looks exactly like a right one.**

   So the engine is fed `bundle.fuel.entries` entire, always. The range is
   applied afterwards, to the rows, and a fill-up whose consumption point was
   computed against an entry outside the window keeps the figure it had. This is
   the same class of defect F4 was built around — "a derived figure that is
   wrong is invisible until it has been wrong for a year" — and the filter is the
   easiest possible way to reintroduce it.

4. **Today comes from the local calendar, once per render.** `todayIso()`, which
   F5 moved into `format.ts` for exactly this kind of caller. Every range
   boundary is derived from it — YTD from the first of January, this month from
   the first of the month, previous month as a whole calendar month — with no
   `Intl`, no locale and no UTC (§3.6, and F4's UTC+3 trap).

5. **The custom range is two fields in the flow, not a calendar.** `GG/AA/YYYY`
   in each, parsed by the `parseDate` that already exists, and an unreadable one
   is simply not applied — the chips remain the truth of what is shown. There is
   no popup calendar because `audit-overlap` forbids the entire family of
   constructs a date picker is built from, and because two text fields in the
   family's own date format are not worse.

6. **An empty range is still the table.** Chips that exclude everything leave the
   headers, the columns and the widths exactly where a filled list would put
   them, with one sentence inside the table (§7 — no "get started" screens, and
   none of Fuelio's "You need to add some data first" either).

7. **The right pane is the detail region.** Selecting a row fills it with that
   record whole — every field of §4.4, including the ones the columns do not have
   room for. This is what F4's comment reserved it for, and it is what replaces
   the tooltip TRITIUM does not have and `audit-overlap` would refuse anyway.
   With nothing selected it holds empty cells, as it does today.

8. **Deletion arrives, and asks twice, in the flow.** F4, F5 and F6 all deferred
   it here. The confirmation is the button changing into a confirming button and
   changing back if anything else is touched — **not** a dialog, a modal or
   `window.confirm`, all three of which `audit-overlap` fails the build over, and
   all three of which cover the record the maker is deciding about.

   Removal goes through the main process by id, rewrites the file through the
   atomic helper, and touches nothing else in it. **Nothing is renumbered**, and
   no two entries can end up sharing an id: `nextId` allocates from the highest
   id present rather than from a count, which is what F2 chose it for.

   Said precisely, because the loose version is wrong: deleting a **middle**
   entry leaves every remaining id where it was and the next allocation still
   continues past the highest. Deleting the **highest** entry does free its
   number for the next one — which is exactly what already happens when the
   maker deletes the last entry in Neovim, and is harmless, because nothing
   outside the file ever refers to an id. Uniqueness within the file is the
   guarantee; monotonicity forever is not, and claiming it would be a promise
   the storage layer never made.

9. **Sorting is by column, and each list keeps its own default.** Fuel by
   odometer descending — §5.2 orders by odometer, and the list should not
   disagree with the engine. Costs and service by date descending, the order
   `entries.ts` already provides. A click cycles ascending, descending, and back
   to the default.

10. **The three panes lose their provisional comments, and F7 gains none.** What
    this milestone builds is the furniture §7 settled, not a stand-in for it.

### 2.2 The ranges — `src/shared/range.ts`

The five of §7.2 plus a custom pair, as pure functions over a date string and
today. Nothing in here reads a clock except through the `now` it is handed, so
every boundary is testable without freezing time.

F8 needs precisely the same five for the charts — §7.2 gives the chips to both —
so this module is written to be used twice and lives in `shared/` from the start
rather than inside a pane that a later milestone would have to reach into.

### 2.3 The table — `src/renderer/panes/EntryTable.tsx`

TanStack's `useReactTable` with the core and sorted row models. The `.entries`
treatment F4b settled is inherited whole: the row height, the alignment, the rule
under each row, the first and last column padding.

Dense means dense — this is the view the maker reads columns of figures in — so
the table stays on the numbers and pushes the prose into the detail pane.

### 2.4 Tests that must exist

- **vitest:** each of the five ranges against a fixed `now`, including the
  turn-of-year cases (YTD on 1 January; previous year from inside January;
  previous month from inside January reaching back into December) · a custom
  range with an unreadable bound falling back rather than filtering to nothing ·
  a range that excludes everything returning an empty list, not all of them ·
  **and the one that matters: the consumption figures over a filtered view being
  identical to the figures over the whole history** — the same fill-up, the same
  l/100km, with a partial fill left outside the window.
- **Playwright:** the chips change which rows are listed · the fuel list's
  consumption column is unchanged by the chip that hides the entry it was
  measured against · a row selected fills the detail pane · a delete asks twice
  and then removes exactly one `[[entry]]` from the file · the next entry added
  after a deletion does not reuse the deleted id · sorting by a column reorders
  the rows · an empty range keeps the headers · all of it with the network
  severed.

## 3. SCOPE — OUT

No charts (F8) — the chips are built here and F8 reuses them, but nothing is
plotted. No summary cards (F9), no statistics (F10). No settings UI (F11): units
stay km, litres and l/100km. **No search, ever** (§7). No column reordering, no
column hiding, no saved views, no pagination — six hundred records over a decade
scroll. No export (§4.1 — the app ships none). No bulk operations: deletion is
one record at a time, which is the only rate at which a maker regrets one.

## 4. ACCEPTANCE CRITERIA

F7 is done when every line below is true:

1. `npm test` is green: the five audits, both tsconfigs silent under `strict`,
   the units, the build, and the e2e suite.
2. All three lists are the same dense table component, carrying §7.2's five chips
   and a custom range.
3. **A consumption figure is identical whether or not a chip hides the entry it
   was measured against.**
4. Selecting a row fills the right pane with that record's every field.
5. Deleting asks twice, removes exactly one `[[entry]]`, and leaves every
   remaining entry — id, fields and unknown keys alike — exactly as it was.
   Deleting a middle entry does not renumber anything, and the next id still
   continues past the highest still present.
6. No dialog, modal, tooltip, popover or absolutely-positioned element exists —
   `audit-overlap` passes.
7. An empty range and an empty file both show the table with its headers.
8. Every figure renders in the family convention — `1.234,56 ₺`, `GG/AA/YYYY` —
   in both languages, with no `Intl` call and no locale read.
9. `writeFileSync` appears nowhere in `src/` outside `atomic.ts`.
10. Zero network: the audits still prove it statically and the offline e2e run
    still behaves identically.
11. No AI attribution exists anywhere in the tree or the git history.
