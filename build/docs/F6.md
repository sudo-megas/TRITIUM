F5 drew §6.1's tree and left one branch of it unwritten. This is that branch.

The evidence is `draft/FORGOTTEN.jpg`, the maker's PERİYODİK BAKIM sheet — four
rows, and the column headings are the record: TARİHİ · PARÇA · KM · TUTARI ·
**ALINDIĞI LİNK / YER**. That last heading is the milestone in five words. It
does not say "link". It says *the link **or** the place*, and the four rows prove
the maker meant both:

| PARÇA | ALINDIĞI LİNK / YER |
|---|---|
| Michelin Primacy 4 S1 235/50R19 103V XL | `https://www.lastikcim.com.tr/lastik/…` |
| Bosch Aerotwin A863S Silecek | `www.sileceksepeti.com` |
| Filtron K 1444A Polen Filtresi | `heryedek` |
| SERVİS | *(empty)* |

A full address, a bare domain, a shop's name, and nothing at all. `vendor` is
therefore **not a URL field**, and XTRITIUM §4.4's instruction — "selectable text
ONLY, never a link" — is not a restriction placed on a link field. It is an
accurate description of a field that was never holding links in the first place.
The spreadsheet renders three of those four cells as blue underlined hyperlinks
because a spreadsheet cannot help itself. TRITIUM can (§3.5).

The fourth row is worth its own sentence. PARÇA reads `SERVİS` — twelve thousand
lira of labour at 15.100 km, with no part and no vendor. `part` is not a
component field either: it is what was done or bought, in the maker's words.

## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

1. **SERVICE is Periyodik Bakım's entry path, and the tab is where it lives.**
   Not a branch of the cost form. §6.2 routes these entries to a different file
   with a different shape, and a form that wrote two files depending on a
   dropdown would be two forms wearing one coat. The SERVICE tab gets its own
   button, exactly as FUEL and COSTS have theirs.

2. **The cost form now says where Periyodik Bakım went.** F5 could not: the
   SERVICE tab was empty, and pointing at an empty tab is worse than saying
   nothing. It is no longer empty, so TEKRAR EDEN carries one line of text naming
   the tab that holds it. The category still does not appear in the picker.

3. **`vendor` is "where it came from", not a URL.** The sheet's own heading is
   ALINDIĞI LİNK / YER and its rows hold an address, a bare domain, a shop name
   and an empty cell. So the field is plain text, stored as typed, and **rendered
   as text that can be selected and copied — never as an anchor** (§3.5). The
   e2e suite asserts what F1's About test already asserts of the whole
   application: `a` appears nowhere in the document.

4. **`part` is what was done or bought.** The maker's fourth row is `SERVİS` —
   labour, no component, no vendor. A field that insisted on a part number would
   have refused the row the sheet actually contains.

5. **The odometer hint is the highest reading the vehicle knows, from any file.**
   F4 built the hint from fuel entries because fuel was the only thing carrying
   an odometer. Service entries carry one too, and a hint that ignored them would
   tell the maker his car had 19.764 km when the last service said 15.100 — from
   the wrong file, confidently. The hint reads fuel **and** service, and a
   backwards reading **warns and is then accepted**, per §5.1 and §3.8.

6. **Nothing watches an interval. Ever.** This is the milestone where a
   maintenance tracker is most tempted to compute "next service due at 25.000 km"
   or to notice that a filter is a year old. §3.3 forbids it in three separate
   clauses — no estimates, no projections *of future entries*, no reminders — and
   §4.4 already says of `inspection_due` that "nothing watches it". The service
   list is a record of what happened, and a `[[entry]]` is created only when the
   maker creates it.

7. **A service entry is added by the main process,** by `service:add`, with the
   id allocated there against the file as it is at that moment; editing keeps a
   by-id `service:update`. Both are `addCostEntry`'s shape, for `addCostEntry`'s
   reason.

8. **Newest-first ordering moves to `src/shared/entries.ts`.** F5 wrote it in
   `costs.ts` when costs were the only dated list without an odometer; service is
   the second, and service code importing cost code to learn how to sort would be
   the wrong shape for a fact neither owns. This is the third time a milestone
   has made this move — `slugFor` and `todayIso` went the same way in F5 — and it
   is worth naming as a habit rather than repeating as a surprise: **the second
   caller is what promotes a helper, not the first.**

9. **F6 deletes nothing.** F7 owns removal, where the list lives.

### 2.2 The form — `src/renderer/forms/ServiceForm.tsx`

A window of its own (§5.1), opened empty or on an existing `entry` id to edit one
(§3.8). Five fields, which is §4.4's `service.toml` entire: date, part, odometer,
amount, vendor.

Save is refused until there is an amount — the one figure without which the row
records nothing. `part` is not required: the maker's own fourth row would have
been rejected by a form that demanded one, since `SERVİS` is a description and
the field it belongs in is the one it is in.

### 2.3 The pane — `src/renderer/panes/ServicePane.tsx`

Provisional, in F4's and F5's pattern: one button and a list — date, part,
odometer, amount, vendor — read from `bundle.service.entries`. F7 replaces it.

The vendor column shows the text as it is. Long addresses are allowed to be long;
F7's dense table decides what to do about width, and guessing now would be
furniture built twice.

### 2.4 Tests that must exist

- **vitest:** the draft ↔ record round-trip, including an empty vendor and an
  empty part · an amount forced positive · the odometer hint taking the highest
  reading across fuel and service rather than fuel alone · a backwards reading
  reported as backwards · the newest-first order with an equal-date tie · the
  §4.4 `service.toml` sample still round-tripping.
- **Playwright:** the service form opens as a **second window** · an entry lands
  as one `[[entry]]` with `id = "s-0001"` in the §4.4 shape · the shell shows it
  **without a restart** — the broadcast F5 flagged · a vendor holding a URL
  renders as text and **the document contains no anchor** · a vendor holding a
  shop name and an entry holding no vendor at all both save · the form reopens an
  entry with every figure identical · the empty pane is the same layout holding
  nothing · all of it with the network severed.

## 3. SCOPE — OUT

No service intervals, no due dates, no reminders, no projections of future
maintenance — §3.3, and decision 6. No dense tables and no range chips (F7); this
list is placeholder furniture and **nothing is deleted**. No charts (F8), no
summary cards (F9), no statistics (F10) — service spending joins the totals when
those milestones compute them. No settings UI (F11). No attachments: receipts and
invoices are PARACHRON's job (§6.2). No opening of any address, ever (§3.5).

## 4. ACCEPTANCE CRITERIA

F6 is done when every line below is true:

1. `npm test` is green: the five audits, both tsconfigs silent under `strict`,
   the units, the build, and the e2e suite.
2. A service entry typed into the form lands in `vehicles/<slug>/service.toml` as
   one `[[entry]]` in the §4.4 shape, with an allocated `id`.
3. All four of the maker's own rows can be entered as they are — including
   `SERVİS` with no vendor, and `heryedek` as a vendor that is not an address.
4. The shell shows a service entry saved in a form window without being
   restarted.
5. **No anchor exists anywhere in the application**, with a URL stored in
   `vendor` and displayed.
6. The odometer hint is the highest reading across `fuel.toml` and
   `service.toml`; a lower reading warns and is then accepted.
7. Nothing in the app computes, displays or stores a future service date,
   interval or reminder.
8. The form is a genuine second window, movable outside the main one, and
   `window.open` is still refused.
9. Every figure renders in the family convention — `1.234,56 ₺`, `GG/AA/YYYY` —
   in both languages, with no `Intl` call and no locale read.
10. `writeFileSync` appears nowhere in `src/` outside `atomic.ts`.
11. Zero network: the audits still prove it statically and the offline e2e run
    still behaves identically.
12. No AI attribution exists anywhere in the tree or the git history.
