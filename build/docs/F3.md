# TRITIUM — F3 · v0.1.2 · «Vehicles»

Repo path of this file: `~/REPO/build/docs/F3.md`
Governing document: `~/REPO/XTRITIUM.md` — where this file and XTRITIUM disagree, XTRITIUM wins.

F3 is the first milestone with something to look at. F1 built the frame and F2
built the storage under it; F3 puts a person in front of both. A vehicle can be
created, edited, and switched between, and the currency question §8 reserves for
first launch is finally asked.

It is also the first milestone the design phase (XTRITIUM §11) gates, so §2.1
records what was settled to unblock it — and, just as deliberately, what was not.

## 1. WHERE F3 SITS

The F-map in `F1.md` §1 is confirmed for this milestone: **F3 · v0.1.2 —
vehicles: records, picker, first-run currency question.**

F2 delivered the layer F3 stands on, and F3 adds no second way to disk:

| Already built (F2) | What F3 does with it |
|---|---|
| `repository.ts` — slugs, directories, whole-vehicle load | the picker lists what it finds; creation allocates through `uniqueSlug` |
| `vehicle-file.ts` — parse/serialise the §4.4 record | the form reads and writes exactly that shape |
| `scaled.ts` — money ×100, pump ×1000, tank ×10 | the form's numeric fields; F3 adds only the *display* layer on top |
| six enumerated IPC channels | joined by `vehicle:create` and one change broadcast |
| `settings.toml` with `currency` deliberately absent | the question that fills it, asked once |

### 1.1 What the design phase settled here — and what it did not

**Settled, for F3:** vehicles are reached by a **picker in the tab bar**, not by a
ninth tab; entry forms are **real popup windows**; the active vehicle is
remembered in `settings.toml`.

**Still open (§11):** the final tab list and pane contents, the visual design of
forms, tables and cards, and the eleven palettes' real values. F1's placeholder
palettes are still what paints the screen. F3 is a flow to judge, not a look.

## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

1. **No vehicles tab; a picker in the tab bar.** §7 fixes the shape as
   "Multiple, with a picker" — a picker is a control, not a tab. The tab list
   stays as F1 drew it, and §11 item 1 stays open for the design phase.
2. **Forms are real, separate, movable Electron windows.** §5.1 already requires
   this of the fuel entry paths ("draggable outside the main one"); F3 builds the
   machinery once and F4 inherits it. F1's refusal of *renderer-opened* windows
   (`setWindowOpenHandler` → deny) stays exactly as it is: the renderer asks the
   main process for a window, and `window.open` remains dead.
3. **The active vehicle is remembered** as `active_vehicle` in `[general]`.
   XTRITIUM §4.4 does not draw this key; F3 adds it, because §3.2 says the app
   opens straight into the data, and a picker that forgets is not that.
4. **The currency question fires on an absent `currency` key**, never on "no data
   directory". A file written before the key existed must still be asked once.
5. **Renaming a vehicle does not move its directory.** The slug is allocated at
   creation and is the directory name for life; a rename edits `name` only.
6. **F3 deletes nothing.** Removing a vehicle would remove every fill-up in it,
   and the app ships no backup and no export (§4.1). The plaintext promise means
   a file manager can do it; the app does not.
7. **Creation writes `vehicle.toml` only.** The three entry files appear when
   their first entry does — a missing file already reads as an empty document.

### 2.2 The family formatter — `src/shared/format.ts`

XTRITIUM §8 fixes presentation for **both** languages: **`1.234,56 ₺`** and
**`GG/AA/YYYY`**. It is a family convention, not a locale, so it is written by
hand on top of F2's `formatScaled` — thousands separated by `.`, decimal `,`,
currency symbol suffixed after a space.

`audit-locale` forbids the bare `Intl`/`toLocaleString` calls outright, and that
is the right constraint: a locale-aware formatter would render this differently
on a machine set to `en_US`, which is precisely the ambient dependency §3.6
exists to forbid.

The module reads as well as writes. The form displays `54,0`, so `parseInput`
takes comma-decimal text back to a scaled integer, and a figure typed, stored and
redisplayed is the same figure. A symbol table covers `TRY ₺`, `USD $`, `EUR €`,
`GBP £`; **an unrecognised code prints as itself**, because the currency is free
text (§8 asks once and fixes it; it never claims to know every currency).

### 2.3 Popup windows — `src/main/windows.ts`

One helper opens a child `BrowserWindow` carrying the same preload, the same
`sandbox`/`contextIsolation` settings and the same navigation guards as the main
window — `harden()` is the one place those refusals are written, and every
window goes through it.

Which form to draw travels in the **process arguments**, beside the settings F1
already passes that way, and `src/renderer/main.tsx` branches on what the preload
read. Not a URL hash: the argument arrives typed, is read once, and reads the
same under the dev server as under a packaged `loadFile` — a hash would have to
be spelled two ways and parsed twice. No second build entry, no router, no new
dependency of any kind.

### 2.4 The picker and the active vehicle

- `src/renderer/state/vehicles.ts` — a zustand store in the shape of
  `state/settings.ts`: the slug list, the active slug, the loaded bundle.
- The picker renders at the right end of the tab bar. With **no vehicles it is
  still there**, empty, beside its Add button — §7 forbids "get started" screens,
  so an empty app is the same layout with nothing in it.
- `vehicle:create` allocates the slug and writes the record. When a form window
  saves, main broadcasts `vehicles:changed` and the shell reloads, so the two
  windows can never disagree about what is on disk.

### 2.5 The vehicle form

Every field of §4.4's `vehicle.toml`, and **no photo field anywhere**. Text for
`name`, `make`, `model`, `engine`, `plate`, `vin`; the `FUEL_TYPES` pick-list for
`fuel_spec`; `tank_capacity_l` at one decimal and `purchase_price` at two, both
through `parseInput`; `purchase_date`, `registration_date` and `inspection_due`
as GG/AA/YYYY.

`name` is the only required field, because it seeds the slug. Everything else
follows §3.8: the form may warn about a suspicious figure, and then it accepts
the maker's word.

### 2.6 The currency question

Opened by the main process at startup when `currency` is absent, modal to the
main window, offering TRY / USD / EUR / GBP and a free-text code. It writes
through the existing `settings:write` merge and is **never shown again** — and no
settings screen will offer to change it (§8: asked once, fixed forever, no rates,
no conversion).

### 2.7 Tests that must exist

- **vitest:** `1.234,56 ₺` and `GG/AA/YYYY` including negatives, zero and a
  figure that drifts in floating point · an unknown currency code printing as
  itself · `parseInput` round-tripping every field's decimals · a rename leaving
  the slug untouched · `active_vehicle` surviving a read-modify-write of a
  settings file that also carries unknown keys.
- **Playwright:** a first launch with no `currency` asks, and the next launch
  does not · a vehicle created through the form lands at
  `vehicles/<slug>/vehicle.toml` and appears in the picker · the picker's choice
  survives a restart · the form is a **second window**, not a div · with the
  network severed, all of it behaves identically.
- **The existing suite is seeded first.** Every current e2e spec launches against
  an empty `XDG_DATA_HOME`, so every one of them would meet the new question. A
  shared launch helper seeds a `settings.toml` carrying a currency before the ask
  is wired, leaving only the first-launch specs to face it.

## 3. SCOPE — OUT

No fuel entry, no consumption engine (F4). No costs (F5), no service (F6). No
lists or tables (F7), no charts (F8), no summary cards (F9), no statistics (F10).
The settings screen gains nothing — units and precision are F11. **No vehicle
deletion.** No photos, ever. No backup, export, import or MIME type (§4.1). No
palette values and no visual design: still §11's.

## 4. ACCEPTANCE CRITERIA

F3 is done when every line below is true:

1. `npm test` is green: the four audits, both tsconfigs silent under `strict`,
   the units, the build, and the e2e suite.
2. On a data directory whose `settings.toml` has no `currency`, the question is
   asked once; the answer is written; the next launch does not ask.
3. A vehicle created through the form exists on disk as
   `vehicles/<slug>/vehicle.toml` in the §4.4 shape, and **only** that file.
4. Editing a vehicle's name leaves its directory name unchanged.
5. The picker lists every vehicle, switches between them, and reopens on the last
   one used after a restart.
6. The form is a genuine second Electron window, movable outside the main one.
7. `window.open` is still refused, and no address anywhere is a link (§3.5).
8. Money renders as `1.234,56 ₺` and dates as `GG/AA/YYYY` in both languages,
   with no `Intl` call and no locale read.
9. A figure typed into the form, saved, and reopened is the same figure.
10. No photo field exists in the record, the form, or the types.
11. `writeFileSync` appears nowhere in `src/` outside `atomic.ts`.
12. Zero network: the audits still prove it statically and the offline e2e run
    still behaves identically.
13. No AI attribution exists anywhere in the tree or the git history.
