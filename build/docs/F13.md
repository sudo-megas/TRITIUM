## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

1. **The package installs an unpacked Electron tree, not an AppImage and not a
   bundled runtime.** `electron-builder` is configured with the `dir` target,
   which produces `release/linux-unpacked/`. The PKGBUILD copies that into
   `/usr/lib/tritium/` and puts a two-line launcher at `/usr/bin/tritium`.

   §2 named electron-builder and §9.3 named `.pkg.tar.zst`; `dir` is the target
   that lets one produce the other. An AppImage would ship a second copy of
   everything the package manager already knows how to track, on a distribution
   whose whole argument is that it tracks things.

2. **The PKGBUILD builds from a git tag, and names it.** §9.3 is explicit. The
   `source` is the repository at `#tag=v$pkgver`, so a package can always be
   traced to a commit, and `pkgver` is the only thing that has to change between
   releases.

3. **Node and npm are `makedepends`, not `depends`.** They build the thing; they
   are not needed to run it. The runtime dependency list is what Electron
   actually links against on a bare Arch install, and nothing more.

4. **The icons come from the maker's own artwork, at the sizes he made.** §9.3
   says the PNGs are supplied into the build path during the build — and they
   already are: `build/icons/` holds 48, 64, 128, 256, 512, 1024, 2048 and 4096.
   The PKGBUILD installs the hicolor sizes that a desktop actually reads (48
   through 512) and leaves the two enormous ones alone, because no icon theme
   looks for a 4096-pixel launcher.

5. **No MIME type, and the desktop file says so by omission.** §9.3 — there is no
   custom file format to claim. `tritium.desktop` declares no `MimeType` and no
   `%f`/`%U` field code, because the application does not open files given to it.

6. **`StartupWMClass` is set, and it matters more here than usual.** F4b's own
   research is the reason: a tiling compositor matches window rules on the
   application id, and TRITIUM's windows were all called TRITIUM until F4b gave
   the form windows their own titles. The desktop entry declares the class so the
   compositor can pair the launcher with the window it opens.

7. **The tooling never touches `megas-xlr`.** §9.3, verbatim. There is no publish
   script, no upload step, no signing key referenced anywhere in this repository.
   The maker signs and places packages himself, and F13 adds nothing that could
   be mistaken for doing it for him.

8. **`npm ci`, not `npm install`, and the lockfile is the input.** A clean chroot
   exists to keep stray host state out; installing from anything but the lockfile
   would let it back in through the front door.

## 4. WHAT THIS MILESTONE COULD AND COULD NOT VERIFY

Stated plainly, because the difference matters and a packaging milestone is the
easiest place in a project to claim more than was done.

**Verified here, by running it:**

- `electron-builder --linux dir` produces `release/linux-unpacked/` with the
  binary, the resources and the locales the PKGBUILD's `package()` expects — the
  paths it copies are the paths that exist.
- `desktop-file-validate` passes `tritium.desktop` with no warnings.
- `makepkg --printsrcinfo` parses the PKGBUILD and prints the metadata, so it is
  syntactically a PKGBUILD and its variables resolve.
- The whole suite still passes: seven audits, both tsconfigs, the units, the
  build and the e2e run.

**Verified by F14's sweep, which is where this section was read again:**

- **The packaged binary launches.** F13 built `release/linux-unpacked/tritium`
  and looked at it with `ls`; it had never been executed, and this section said
  as much while `packaging/README.md` §3 offered running it as the quick look.
  F14 ran it against a throwaway `XDG_DATA_HOME` and watched the process tree: a
  GPU process on Wayland and **two renderers** — the main window and the
  first-launch currency question, which is exactly what §8 says a first launch
  is. No output on stderr, and it shut down cleanly.

**NOT verified here, and it must be the maker who does:**

- **The clean-chroot build.** `extra-x86_64-build` is `devtools`, needs root, and
  builds by **fetching the tag from the remote** — so it cannot run until the tag
  has been pushed. That is §9.3's own procedure and it belongs on the maker's
  machine, after `PUTAGREL`.
- **`namcap`** on the built package. Not installed here.
- **Installing the package and launching it from a desktop.** The binary has now
  been run from the build tree; running it from `/usr/bin` after `pacman -U`,
  with the launcher matching `StartupWMClass`, is still a different claim and
  this milestone does not make it.

`packaging/README.md` carries these as the commands to run, in order, so the
maker is not reconstructing them from this document.

   key, no publish step, no AUR file, no CI. The name appears in exactly two
   comments, both of which say that nothing here touches it, which is a
   different thing from a reference that does.

   maker can run.
8. No AI attribution exists anywhere in the tree or the git history.
