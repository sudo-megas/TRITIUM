# TRITIUM — F15 · v0.2.5 · «Design Rework»

Repo path of this file: `~/REPO/build/docs/F15.md`
Governing document: `~/REPO/XTRITIUM.md` — where this file and XTRITIUM disagree, XTRITIUM wins.

F14 closed the desktop phase and called the application finished. Then the maker
opened it and found seven defects, three ranked critical and one — the entry
forms — ranked "FEDERAL LEVEL — BLACK CRITICAL", with the note that **all popups
are dead**.

He is right, and the arithmetic below shows he is right by a wider margin than
the screenshots do. What makes this milestone worth writing carefully is not the
defects themselves but the fact that **every one of them is a promise F4b already
made and this implementation did not keep**:

| Found by the maker | Already decided, and not delivered |
|---|---|
| Headings smaller than the content under them | **D10** — the type scale "is derived, not invented" |
| Separators like "thin fibers" | **D4** — depth from borders; bevel and inset permitted |
| Buttons square and small | **D11** — radius 0/2/4/8, square **only** on the tab bar |
| Controls overlapping controls | **D1** — "Nothing overlaps, and it is enforced mechanically" |
| Palettes with no names | **D3** — names all eleven |

F4b stated the standard this milestone is held to, and stated it well:

> The glory comes from craft, not decoration… exact alignment, a spacing rhythm
> that never breaks, **a type scale with real intervals**, colour only where it
> carries meaning, and **edges that are deliberate at every boundary**.

F15 does not argue with any of that. F15 is the milestone that makes it true in
the pixels.

## 1. WHERE F15 SITS

**F15 is v0.2.5**, riding the map §9.1 now prints. It is the first milestone
after the desktop phase was declared complete, which is itself worth recording:
the phase was declared complete on the strength of a green suite, and the suite
was green.

`build/docs/issues.md` closed at twenty-one issues, none open. F15 reopens it at
**I-22 through I-32**.

### 1.1 Why seven audits and 112 tests saw none of this

This is the part of F15 that matters more than any single fix.

**`audit-overlap.mjs` is a regex denylist over source text.** It reads lines
looking for `position: absolute`, `z-index`, `float`, negative margins,
`box-shadow`, `backdrop-filter`, the Popover API, `<dialog>`, `role="dialog"`,
`title=`. It is a good gate and it works. **Not one of the defects the maker
found uses any of those constructs.** Every overlap in this milestone is ordinary
in-flow CSS Grid track arithmetic: a fixed track, an item with a `min-width`
larger than it, and no `overflow` to clip the difference. A gate that reads
source text cannot see two boxes landing on the same pixels.

**`overflow.spec.ts` measures the wrong thing in the wrong places.** It computes
`scrollWidth − clientWidth`, which detects content wider than its container. Two
elements can overlap perfectly while the container never scrolls — which is
exactly the Settings case. It covers `fuel`, `costs`, `service`, `summary`,
`charts`, `statistics`. It does **not** cover `settings`, and it does not open a
single form window.

**Across all fifteen e2e specs, the intersection of "opens a form window" and
"asserts geometry" is empty.** Nine specs open form windows. Every assertion on
them is about field values, disk contents or window identity. The closest near
miss is four tests named *"the form is a separate window, anchored to nothing"* —
which check `BrowserWindow.getParentWindow()` and `isMovable()`, OS-level
properties, never a bounding box.

So D1 has been, for eleven milestones, **a rule about how the source is written
rather than a fact about what is drawn**. The single most important thing F15
ships is not a fix. It is `tests/e2e/geometry.spec.ts`, which measures it.

## 2. SCOPE — IN

### 2.1 The decisions this milestone settles

**1 — The type scale grows at the top and holds at the bottom.**

The scale was never missing. `tokens.css` has carried a derived eight-step ramp
since F4b, and every `font-size` in `base.css` consumes a token — there is not
one bare pixel value. The defect is that the ramp is **applied wrongly at the one
place hierarchy is decided**:

```
.section__title  →  --text-xs   = 11px
.field__label    →  (unset, inherits body --text-base) = 13px
```

A section heading two pixels **smaller** than the label beneath it. And the
codebase contains its own control group: `.form__title` does the identical visual
job — uppercase, tracked, an eyebrow above a group of fields — and correctly uses
`--text-md`, which `tokens.css`'s own comment labels *"section headings"*. So
`.section__title` is not a house style. It is the sole outlier in its own
stylesheet, contradicting the token file's stated intent.

The comment above it explains the choice: tracking, not size, is what separates
the heading from the body. That is Material's small-and-soft header treatment,
and **D9 already ruled it unavailable here** — Material compensates with a medium
weight, and the vendored font has no medium weight. F4b saw that route close;
this rule walked through it anyway.

The ramp rises where hierarchy is read and holds where density is read:

```
pane title    --text-lg     19 → 26
section head  --text-md     15 → 22
card / sub    --text-card    —  → 18
body / label  --text-base    13 → 16
table cell    --text-sm      12 → 14   ← held
meta / units  --text-xs      11 → 12   ← held
```

Table cells and meta text are **deliberately not scaled with the rest.** §7.1
requires Summary's trend cards "all visible at once — no carousel", D12 fixes
dense rows at 32–36px, and F4b measured the height budget as already tight:
*"1366 × 768 does not [have room], clearing 720 by fourteen pixels."* Growing the
chrome is what the maker asked for; growing the table would spend a budget that
§7.1 has already committed.

**2 — Chart text joins the application.** ECharts is never given a `fontFamily`
or a `fontSize`, so every axis label, legend and tooltip in all seven charts
renders in ECharts' own default sans at its own default size. §8 says
CaskaydiaCove Nerd Font Mono **for the whole UI**. Seven charts are not an
exception anyone wrote down; they are an omission. The tokens are read off the
document — `Chart.tsx` already does exactly this for colour — and handed to
ECharts.

**3 — A palette shows its name.** The swatch is a 56 × 36 button holding three
empty `<span>`s. It has no text at all. The names exist, in full, in both
catalogues under `palettes.*`, and are already passed as `aria-label` — readable
by a screen reader and invisible to the man using the mouse.

The fix is **a caption, not a tooltip**: `audit-overlap.mjs` bans the `title`
attribute by name, because a native tooltip draws over whatever is beneath it.
Each palette becomes a card carrying the swatch, the name, and a **LIGHT/DARK**
tag — the classification `palettes.css` already records in its per-palette
headers. The `<select>` above the grid becomes redundant and goes.

**4 — `--measure-control` stops being a floor, and this is the whole of the
popup disaster.**

`.control` declares `min-width: var(--measure-control)` — 224px. An author's
explicit `min-width` overrides a grid item's automatic minimum, so it is immune
to the `minmax(0, 1fr)` that everything else relies on. Wherever a track is
narrower than 224px, the control paints straight over its neighbour, unclipped,
because no rule in the chain sets `overflow`.

It appears twice, and both times the maker found it:

*The forms.* `.form__grid` is `repeat(2, minmax(0, 1fr))`. `.field` inside it is
`176px | 1fr` with a 16px gap, so each field's real minimum is
**176 + 16 + 224 = 416px**. No form window gives it that:

| Form | Window | − form padding | ÷ 2 columns | Needs | Short by |
|---|---|---:|---:|---:|---:|
| `fuel-quick` | 480 | 416 | 200 | 416 | **216px** |
| `fuel` | 620 | 556 | 270 | 416 | **146px** |
| `cost` | 680 | 616 | 300 | 416 | **116px** |
| `service` | 680 | 616 | 300 | 416 | **116px** |
| `vehicle` | 760 | 696 | 340 | 416 | **76px** |
| `currency` | 460 | 396 | — | 416 | **20px** |

Row-major placement then predicts the screenshot exactly. `VehicleForm`'s field
order pairs `name|make`, `model|engine`, `plate|vin`, `year|fuel_spec`,
`tank_capacity|purchase_price` — and the maker's screenshot shows Make over
Name's input, Engine over Model's, VIN over Plate's, Fuel over Year's, and
Purchase price over the Tank capacity row. Five predictions, five hits. Later
siblings paint over earlier ones, so column two's label lands on column one's
overflowing input.

**All six forms are undersized.** `currency` escapes visible overlap only because
it has no second column to spill into — it is short by twenty pixels regardless.
"ALL POPUPS DEAD" is not hyperbole; it is the arithmetic.

*The settings.* `.field--inline` sets `flex-direction: row` on an element that is
`display: grid`. `flex-direction` does nothing to a grid, so the row stays
`176px | 1fr`: the input lands in the 176px track and paints to 224px, while the
Add button starts at 184px. **They overlap by about forty pixels**, which is what
the maker photographed.

**5 — Three variants were broken by one mistake.** `.field--check` carries the
same inert `flex-direction` as `.field--inline`. Both meant `display: flex` and
neither said it. And `.field__hint` is a third child of a two-column grid, so
auto-placement drops it into row two, column **one** — under the label rather
than under the input it explains. That is the stranded hint text in the Quick add
screenshot.

**6 — Edges become deliberate at every boundary.** Every structural divider in
the application is one pixel of the weaker `--border`. Exactly two lines in the
whole stylesheet use the 2px `--border-strong` tier. Table cells carry
`padding: var(--space-0) var(--space-8)` — **zero vertical padding** — so the
rule sits flush against the row with nothing to breathe against.

Structural dividers move to `--border-strong` at `--border-width-strong`, with an
`inset` highlight for the "2.5D" the maker asked for. D4 sanctions this
precisely: *"Depth comes from fill steps and borders. Outer shadow is forbidden;
inset and bevel are not."* No outer `box-shadow` is added anywhere, and padding
lands on D11's 8px ladder.

**Table row rules stay single, light and unstriped.** D12 argued that from
sources, and the maker's complaint is about chrome and region boundaries, not
about row stripes.

**7 — Controls are rounded and half again as large.** `.button` is 24px tall with
12px text and a 2px radius; `--radius-lg` is used on nothing interactive in the
entire application, only on the scrollbar thumb. Heights go through the tokens —
never a bare pixel in a component rule, which is F4b's own acceptance criterion 8
— and the radius moves off `--radius-sm`.

**The tab bar keeps radius 0.** D11 fixes that from Fluent, with the rule that
corners are not rounded where two elements abut or meet a screen edge, and the
tab bar does both. The maker asked for the buttons "in the pages"; the tab bar is
not in a page.

**8 — Charts go two to a row, and keep their chips.** The stack was a considered
decision with its reasoning in the stylesheet: a chip row, a three-way toggle and
a fullscreen button "do not fit under a 628-pixel card". The maker has ruled the
other way and supplied the reason — the fullscreen button already exists for
detail, and it *replaces* the grid rather than covering it, so no overlay is
implied. Each card keeps its own chips per §7.2, condensed and permitted to wrap.
`Chart.tsx` needs no change: it already carries a `ResizeObserver`. The old
reasoning is corrected in place rather than deleted.

### 2.2 What is written

| File | Change |
|---|---|
| `src/renderer/styles/tokens.css` | the ramp, control heights, radii, border widths |
| `src/renderer/styles/base.css` | `.section__title`, `.control`, `.field*`, `.charts`, `.button`, `.chip`, the dividers |
| `src/renderer/panes/SettingsPane.tsx` | palette cards carrying name and scheme |
| `src/renderer/panes/ChartsPane.tsx` | a head that fits half a pane |
| `src/renderer/panes/Chart.tsx` | ECharts given the family and the scale |
| `src/main/windows.ts` | `useContentSize`, and `FORM_SIZES` re-derived |
| `src/renderer/i18n/{en,tr}.json` | the LIGHT/DARK tags |
| `tests/e2e/geometry.spec.ts` | **new** — the gate that measures D1 |

`src/renderer/forms/*.tsx` are **not touched**. All six windows load one
byte-identical stylesheet, so the entire form repair is three rules in
`base.css`. That is why the worst defect in the milestone has the smallest diff.

### 2.3 The gate, and the gate's own defect

`tests/e2e/geometry.spec.ts` opens **every form window** and **every tab,
Settings included**, at the 1280 × 720 minimum, and asserts:

- no two laid-out boxes intersect unless one contains the other, by
  `getBoundingClientRect`
- nothing overflows its container, by `scrollWidth − clientWidth`
- **no section heading is smaller than the text it heads**, by computed
  `font-size` — which is acceptance criterion 2, and the property D9 leaves size
  solely responsible for

It uses the existing `windowWith(app, '<x>-save')` harness, so it opens forms the
same way every other spec does. Eighteen tests, which is where the suite's 130
comes from: 112 before this milestone, plus these. D1 stops being a claim about
source text.

**It was wrong the first time, and that is recorded as I-29 rather than quietly
corrected.** The first version compared **siblings** — every pair of child boxes
under each parent — which is the obvious reading of "nothing overlaps". It passed
against a build with the popup defect deliberately put back.

The reason is the shape of the defect, and it is worth understanding because it
is the reason the whole class went unseen for eleven milestones: the label that
sat on top of an input **was not that input's sibling**. `.form__grid` held one
`.field` per column, and the overflowing control in column one ran under the
label of the field in column **two** — a cousin, two subtrees apart.

Comparing every pair and excluding only true ancestry fixes it, and the gate now
names what it finds:

```
input[fuel-odometer_km].control overlaps span.field__label
input[method-input].control overlaps button[method-add].button
```

Those two lines are the maker's two screenshots, in text.

The practice that caught it is the point: **the defect was put back and the test
was watched to fail before it was trusted to pass.** Without that step this
milestone would have shipped a green gate over a broken property, which is worse
than no gate — a passing suite is read as evidence, and this project has just
spent a milestone learning what that costs.

## 3. SCOPE — OUT

No change to the font (§8). No third weight (D9). No in-page modals — forms stay
movable popup windows (§7), and D1 forbids modal-over-content. No outer shadow,
no `backdrop-filter`, no overlay token (D1, D4, D13). No negative margins (D11).
No rounding on the tab bar (D11). No zebra striping (D12). No change to the
1280 × 720 minimum (§7). No new palette and no change to any published palette's
values (D3). No animation added — motion stays opt-in (D16).

## 3.1 THE SECOND PASS

The first pass was shown to the maker and he found more, which is the point of
showing it to him. Two were real (`issues.md` I-30, I-31) and one was not. A third pass followed
(I-32).

**I-30 — the vehicle picker fell out of the tab bar.** The type scale widened
every tab label, the bar's contents came to about 1370px in a 1280px bar, and
`flex-wrap: wrap` did exactly what it was written to do. Nothing failed and no
test looked. This milestone's own lesson, recurring **inside** the milestone: a
widening change was made and the one place where width rather than legibility is
the binding constraint was not re-measured. Tab labels are chrome and now take
`--text-sm`; `geometry.spec.ts` asserts every child of the bar shares one `top`.

**I-31 — a stronger line is still only a line.** The first pass answered "thin
fibers" with 2px of `--border-strong`, and the maker's verdict was **"still
primitive"**. He is right: thickness is not depth. Separators now carry an inset
groove, and the two panes stop being divided by a gap and become **planes** —
`--surface-sunken` ground, `--surface` pane, strong border, radius, and an inset
highlight along the top inner edge. A fill step, a border and a bevel: three of
D4's own instruments, and still not one outer shadow in the stylesheet.

That last part changes a recorded decision. The boundary between the panes was
owned by the gap so that neither could paint over it; it is now owned by each
pane's own border. It is symmetrical, so neither can encroach, and it is written
into the stylesheet where the old reasoning was rather than replacing it silently.

It cost width twice — the costs and fuel lists went 3px and 10px over their panes
once the borders and padding were added, and `--measure-prose` plus the table's
cell gutter paid for it. **No figure column was narrowed.** A number that elides
is a number that lies.

### The third pass

Shown the second, the maker asked for the pane outline **twice as thick** and for
the tabs to be **separated, outlined and rounded until they read as buttons**
(`issues.md` I-32).

The first is the same correction as I-31 one tier up. A pane was wearing the
width used by a row *inside* a pane, so the edge of a region and the edge of a
row within it spoke at equal strength. `--border-width-heavy: 4px` exists for the
edge of a whole region and nothing smaller. The colour tier could not move — D4
already spends `--border-strong` at 3.0–3.3 : 1 and there is nothing above it —
so width was the axis left, and no palette is asked for anything new.

The second is a **reversal of a judgment this document made**, and it should be
read as one. F15's first pass took the maker's "all selectable buttons in the
pages can be rounded" to exclude the tab bar, on D11's authority, and said so as
a call he might want to reverse. He reversed it.

D11 did not have to be overruled. It takes radius-0 from Fluent together with
Fluent's stated reason — *"corners are not rounded where two elements abut or
meet a screen edge"* — and both halves are **conditions**. Separating the tabs
removes the abutting; a tab does not meet a screen edge, the bar does, and the
bar is still square. The premise is gone, so nothing the rule protected is lost.
This is the second time in this milestone that reading a rule's own justification
rather than its conclusion turned an apparent conflict into no conflict at all —
the first was I-10's "amendments are the maker's".

Every divider in the bar went with it: between tabs, beside the mark, beside the
picker. A gap and a rule are two answers to one question. Selected state moved to
the tab's own border colour, and the border *width* deliberately does not change
with state, because D12 forbids a size change on a state change and a thicker
edge would reshuffle the whole bar on every click.

It cost about 90px of a bar that must stay one row at 1280. The tabs' padding
paid for it — and this time `geometry.spec.ts` was already watching, which is the
first width change in this milestone that was made under a gate rather than
discovered after one.

The tabs kept one thing from being regions, and the maker caught it at once:
`align-items: stretch` made each exactly as tall as the bar. Correct for a tab
that *is* a slice of the bar; wrong for a button, which needs edges of its own
that the container's edges are not. They are centred now at
`--control-height-sm`, the height every other button here is built to.

That broke this milestone's own one-row gate, and the gate was right to break.
It compared each bar child's `top` and demanded one value — sound while every
child was stretched to a single height, wrong the moment they were deliberately
different heights. It compares **centres** now: children on one line share that
line's centre whatever their heights. Confirmed by forcing a real wrap and
reading the numbers, 63px of spread against a 36px threshold, rather than by
assuming a rewritten test still worked. That is the third time in F15 that a
gate was re-verified by breaking the thing it watches; it is becoming the
milestone's actual method.

### What was reported and was not a defect

The maker reported that **no add popup worked** — every form window opening
blank — and that the **About mark had become a broken image**. Both were true on
his screen. Neither was a defect in this application.

The dev server had been stopped while his copy was still running. `npm run dev`
serves the renderer from Vite, so the already-painted main window kept what it
had while every *new* window had nothing to load from. Blank forms and a broken
image are precisely what that looks like, and they are indistinguishable from
catastrophe.

This was **verified rather than argued**: the built application was launched and
screenshotted, and the vehicle form lays out its two columns correctly while the
About mark decodes. The rule that follows is short — do not stop
`electron-vite dev` while the app under inspection is still open — and the
method is the one this whole milestone is about. The maker's report was
plausible, serious, and describing something real; the only way to know which
thing it was describing was to look.

## 4. ACCEPTANCE CRITERIA

F15 is done when every line below is true:

1. `npm test` is green: seven audits, both tsconfigs under `strict`, the units,
   the build, and the e2e suite **including `geometry.spec.ts`**.
2. **No section heading is smaller than the text it heads**, anywhere.
3. Every one of the six form windows opens with **no overlapping boxes and no
   horizontal scrollbar**, and the geometry spec proves it rather than a person
   reporting it.
4. The Settings add-a-method row does not collide, at either language.
5. All eleven palettes show a readable name and a LIGHT or DARK tag, with no
   `title` attribute anywhere.
6. Charts render two to a row, each keeping its own range chips; fullscreen still
   replaces the grid rather than covering it.
7. Chart axis text renders in CaskaydiaCove at a size from the ramp.
8. Structural dividers read as deliberate edges; table rows keep one light rule
   and no zebra.
9. No bare pixel value is introduced into a component stylesheet — every
   geometry change goes through `tokens.css` (F4b criterion 8).
10. `issues.md` carries I-22 … I-32 with the measurements, not the impressions.
11. No AI attribution exists anywhere in the tree or the git history.
